# Remote Attestation Data Release

Backend foundation for releasing protected data only after a remote workload presents verifiable evidence that satisfies an explicit policy.

The service is intended to grow around attestation formats, verifier trust roots, nonce and freshness controls, policy evaluation, confidential data envelopes, one-time release grants, workload identity, revocation, audit evidence, key rotation, tenant isolation, rate limits, failure recovery, and operational observability. Every release decision must remain explainable and auditable without exposing the protected payload or private key material.

## Development

Requires Python 3.12 or newer.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[test]'
pytest -q
uvicorn proof_release.app:app --reload
```

The API exposes `GET /health`, which returns a JSON readiness result, and a random-challenge flow:

- `POST /v1/challenges` issues a one-time random challenge (nonce) bound to a tenant and workload, with a bounded TTL.
- `POST /v1/challenges/{challenge_id}/consume` consumes a pending, unexpired challenge by presenting its nonce to prove freshness.
- `POST /v1/evidence` receives attestation evidence for a pending, unexpired challenge. The JSON body must include `tenant_id`, `workload_id`, `challenge_id`, `nonce` (unpadded base64url), `evidence_format`, and `evidence`. On success it returns `201` with `evidence_id`, `challenge_id`, status `received`, and a UTC RFC3339 `received_at`, and consumes the challenge in the same transaction so it cannot be reused. Only the SHA-256 digest of the evidence is persisted — never the evidence itself. Errors: `404` unknown/mismatched challenge, `401` wrong nonce, `409` already consumed or received, `410` expired, `422` invalid fields.
- `POST /v1/evidence/{evidence_id}/verify` verifies previously received evidence. The JSON body must include non-empty `tenant_id`, `workload_id`, `nonce` (unpadded base64url) and `evidence` (non-empty string). Only evidence belonging to the same tenant and workload, together with its challenge, is processed: the nonce is checked against the challenge and the evidence is checked to be byte-identical to what was received (SHA-256 digest comparison). The first verification settles the record atomically (`verified` or `rejected`); later calls return the stored conclusion and never re-run the verifier. Both outcomes return `200` with `evidence_id`, `challenge_id`, `status` and a UTC RFC3339 `verified_at`. Errors: `404` unknown/mismatched evidence, `401` wrong nonce, `422` invalid fields/format or evidence digest mismatch (including an `evidence_format` with no registered verifier), `500` verifier plugin failure or, for X.509 evidence, an unavailable revocation registry (no partial state is left behind; the evidence stays `received` and can be re-verified after recovery). As with receipt, the raw evidence is never persisted, logged, or returned — only its digest, the settlement status, timestamp, and a fixed service-defined result code (`accepted`/`rejected`) derived solely from the verifier's verdict are stored.
- `POST /v1/trust-roots` configures an attestation trust root for a tenant and workload. The JSON body must include non-empty `tenant_id`, `workload_id` and `root_pem`, plus an optional non-empty `name`. `root_pem` must be a parseable X.509 CA certificate; anything else (including any private-key material) is rejected and never stored. On success it returns `201` with `root_id`, `tenant_id`, `workload_id`, `name` and a UTC RFC3339 `created_at`. Trust roots are persisted and survive restarts. Errors: `409` the same certificate is already configured for this tenant and workload, `422` invalid fields, unparseable PEM, or a non-CA certificate.
- `POST /v1/trust-roots/{root_id}/retire` retires a configured trust root — a terminal `active` -> `retired` transition that happens exactly once. The path `root_id` must be a canonical lowercase UUID (a missing, blank, whitespace-padded or non-canonical value is `422` and never reads or modifies the root); the body carries exactly two non-empty strings, `tenant_id` and `workload_id` — a missing, blank, wrong-typed, incomplete or unknown field is `422` and writes no state. An unknown root or one whose ownership disagrees with either body field is an indistinguishable `404` (existence is never revealed). On the first legal request the row is atomically set to `retired` with its first-and-final UTC RFC3339 `retired_at`, under the same trust-root row lock X.509 verification takes; success returns `200` with compact JSON containing exactly `root_id`, `status` (fixed `retired`) and `retired_at` in that key order, all JSON strings, terminated by a single newline (no floats or non-finite values, no extra metadata). A repeat retire returns `409`, rewrites neither `retired_at` nor any other state and appends no audit or other record; concurrent retires of one root settle as exactly one `200` plus stable `409`s. A write or commit failure returns `500` after a full rollback, leaving the original status and time intact (and the same request succeeds after recovery). Retirement survives restarts. Retiring a root does not erase or alter anything else — HMAC format handling, custom plugins and existing revocation registrations are unchanged — and the same certificate still cannot be re-created under the same tenant and workload (still `409`), so retirement cannot be bypassed.
- `POST /v1/revocations` registers a trust-root-scoped X.509 certificate revocation. The JSON body must include non-empty `tenant_id` and `workload_id`, a canonical lowercase-UUID `trust_root_id` that belongs to exactly that tenant and workload (an unknown or cross-scope root is an indistinguishable `404`), `certificate_fingerprint` as the unpadded base64url SHA-256 of the certificate's DER encoding (exactly 32 raw bytes, no padding), and `effective_at` as a UTC RFC3339 timestamp (`Z` or `+00:00`; a naive or non-UTC offset is rejected). A missing, blank, wrong-typed or malformed field returns `422` and writes no state. A past effective time is in effect immediately; a future one takes effect once that instant arrives. On success it returns `201` with compact JSON containing exactly `revocation_id`, `trust_root_id`, `certificate_fingerprint` and `effective_at`; registrations are persisted, survive restarts, and never store certificate material or secrets. Within one trust root the same fingerprint is registered at most once — a repeat (including one with a different effective time) returns `409` and never merges or overwrites the first registration — while distinct fingerprints under the same root are independent rows; concurrent duplicate registrations settle with exactly one `201`, every loser receiving a stable `409` and no duplicate row. The scope, trust root, fingerprint and effective time are a single atomic write: any failure during the locked lookups or the insert/commit returns `500` after a full rollback, leaving no half record (and the same registration succeeds once storage recovers). Revocations are isolated per tenant and workload and are scoped to a single trust root — a registration under one root never affects evidence anchored to another root even for an identical certificate.
- `GET /v1/revocations` is the read-only revocation registry query: it lists registered revocations for one tenant/workload/trust root in stable `(effective_at, revocation_id)` ascending order with keyset pagination; the request body is always empty (any non-empty body, including whitespace, is a `422` before any state is read) and no other query parameters are accepted. `tenant_id`, `workload_id` and `trust_root_id` (a canonical UUID) are required non-empty query parameters. Results may be narrowed by `revocation_id` (a canonical UUID), `certificate_fingerprint` (canonical unpadded base64url of exactly 32 bytes), and by an inclusive effective window `effective_after`/`effective_before`, both explicit UTC RFC3339 timestamps (`Z` or `+00:00`; a naive or non-UTC offset is rejected); `effective_after` must not be later than `effective_before`. A missing/blank/whitespace/typed-wrong parameter, an unknown parameter, an illegal identifier, fingerprint or timestamp, or an inverted window returns `422` and writes no state. An explicit `trust_root_id`, `revocation_id` or `certificate_fingerprint` that is unknown, belongs to another tenant/workload, or (for the fingerprint and revocation id) to another trust root returns one indistinguishable `404` without revealing which; a query with no explicit resource whose filters match nothing is simply an empty range. Pagination is cursor-driven: omitting `cursor` or sending an explicit empty string starts before the smallest registration, and the exclusive cursor boundary is the last returned `(effective_at, revocation_id)` position. Cursors are opaque, HMAC-authenticated tokens carrying a distinct revocation cursor kind tag, bound to the scope, every active filter *and* the fixed replayable snapshot — a forged, tampered, cross-scope, cross-filter or foreign-family (rewrap batch, release-grant audit, compliance audit) cursor returns `422` and reads no state. The first (cursor-less) query of a range fixes a replayable snapshot: replaying any of its cursors always returns the identical page in the identical order, never duplicating or skipping an entry and unaffected by registrations committed concurrently or afterwards; registrations committed after that first query appear only in a new cursor-less first query. The compact JSON response, terminated by a single newline, has keys in exactly the order `revocations`, `next_cursor` (empty at the end), `complete`; each entry contains only the four JSON-string fields `revocation_id`, `trust_root_id`, `certificate_fingerprint` and `effective_at` (in the registration response order) — no floats, `-0.0` or non-finite values ever appear, and the query neither computes nor rewrites a certificate's current status: future-effective registrations are listed with their recorded time. The handler issues only reads of committed state, never writes, settles, creates an audit row or modifies a registration, and returns no half page: a registry/storage failure is a `500` with no partial result. Registration creation, concurrent uniqueness, future effectiveness and the X.509 real-time rejection behavior are unchanged.
- `POST /v1/workload-identities` registers a workload identity profile that constrains which X.509 leaf certificate an anchored chain may present. The JSON body must include non-empty `tenant_id` and `workload_id`, a canonical lowercase-UUID `trust_root_id` that belongs to exactly that tenant and workload (an unknown or cross-scope root is an indistinguishable `404`), and a non-empty `claims` list. Each claim is an object with three required non-empty strings, `issuer`, `subject` and `uri`, holding the *parsed* comparison values of a leaf certificate: the issuer distinguished name and subject distinguished name rendered as RFC4514 strings (e.g. `CN=test-intermediate`), and one subjectAlternativeName URI (e.g. `spiffe://example.org/workload/payments`); a missing, blank, wrong-typed or malformed field, a non-canonical UUID, an empty `claims` list, a claim missing/blank on any of the three fields, or any unknown extra field returns `422` and writes no state. On success it returns `201` with compact JSON containing exactly `profile_id`, `tenant_id`, `workload_id`, `trust_root_id`, `claims` (the de-duplicated claims in first-seen order) and a UTC RFC3339 `created_at`; profiles are persisted, survive restarts, and store only the non-sensitive comparison strings — never certificate material, evidence, private keys or secrets. Claims compare as an unordered set: within one trust root, registering the identical claim set (regardless of entry order or duplicate entries) returns `409` and never overwrites the first profile, while a different claim set is saved as an independent profile. The profile and all its claims are one atomic write taken under the trust-root row lock; a failure during the locked lookups or the insert/commit returns `500` after a full rollback, leaving no half profile. Concurrent registrations of the same claim set under the same trust root settle with exactly one `201` and stable `409`s for every loser (a unique `(trust_root_id, claim-set fingerprint)` constraint backs this), and distinct sets never conflict.
- `GET /v1/workload-identities` queries registered profiles. The request body is always empty (any non-empty body, including whitespace, is a `422` before any state is read) and the range is fixed entirely by query parameters: required non-empty `tenant_id`, `workload_id` and `trust_root_id` (a canonical UUID), plus an optional canonical `profile_id`. A missing, blank, wrong-typed or malformed parameter (including an unknown query parameter) returns `422`; an explicitly named `profile_id` that is unknown or outside the tenant/workload/trust-root range returns `404`; an unknown trust root with no profile filter is simply an empty range. On success it returns `200` with compact JSON (single trailing newline) containing an array of profiles sorted by `created_at` then `profile_id`; an empty range is `[]`. Each element carries the registration fields (`profile_id`, `tenant_id`, `workload_id`, `trust_root_id`, `claims`, `created_at`) plus the lifecycle `status` (`active` or `revoked`); revoked profiles remain listed here. The handler issues only reads of committed state, and a registry failure is a `500` with no partial result.
- `PUT /v1/workload-identities/{profile_id}` replaces a profile's complete claim set. The path identifier must be a canonical lowercase UUID with no surrounding whitespace (a missing, blank or malformed identifier, including an empty path segment, is `422`). The JSON body carries the same fields as registration — non-empty `tenant_id`, `workload_id`, canonical `trust_root_id`, and a non-empty `claims` list with the same per-claim rules — and a missing, blank, wrong-typed, empty, malformed or unknown field returns `422` and writes nothing. The profile must exist in exactly the body's scope and trust root (unknown/cross-scope is `404`); an already-revoked profile is terminal and a replacement attempt returns `409` and moves nothing, even when the submitted set equals its last committed set. The replacement is whole-set: the old claims are deleted and the new ones inserted in one atomic transaction with the profile row, so `profile_id`, ownership/scope and `created_at` never change, while `updated_at` is set; a write or commit failure returns `500` after a full rollback and the old claims, status and timestamps are all unchanged. Resubmitting the profile's own current claim set (any order, duplicates collapsed) is an idempotent no-op returning `200` with the current result and never minting or rewriting `updated_at`; requesting a set already owned by a *different* profile under the same trust root returns `409` and moves nothing; concurrent updates based on the same original set settle with exactly one effective write — a request whose requested set just won is answered `200` with that current result, any other stale write receives `409`, and a revocation racing the replacement leaves the revoked profile's last set intact. Success returns `200` with compact JSON containing the original profile fields (`profile_id`, scope, `trust_root_id`, `claims`, `created_at`) plus a UTC RFC3339 `updated_at`.
- `DELETE /v1/workload-identities/{profile_id}` revokes a profile. The path identifier must be a canonical lowercase UUID with no surrounding whitespace (an empty or malformed segment is `422`) and the JSON body carries exactly `tenant_id`, `workload_id` and `trust_root_id`; a missing, blank, wrong-typed, malformed or unknown field returns `422` without writing state. An unknown profile or one outside the body's scope/trust root returns `404`. The active → `revoked` transition is a single guarded atomic update under the trust-root lock; repeating the revocation returns `409` and never rewrites the stored `revoked_at`, and a write/commit failure returns `500` after a full rollback, leaving the profile, status and revocation time unchanged. Success returns `200` with compact JSON containing the original profile fields plus `"revoked": true` and a UTC RFC3339 `revoked_at` (and the existing `updated_at` when the profile had been replaced). A revoked profile stays queryable with status `revoked` but no longer participates in X.509 identity gating; its last committed claims are retained.
- `POST /v1/policies` creates a versioned release policy scoped to a tenant and workload. The JSON body must include non-empty `tenant_id`, `workload_id`, `name` and `rule`. A rule is exactly one of `{"claim": "<top-level claim name>", "equals": <scalar>}` (scalar = string, number, boolean or null), `{"all": [rule, ...]}`, `{"any": [rule, ...]}` (both non-empty lists) or `{"not": rule}`; any other shape is rejected with `422`. Creating a policy with an existing `(tenant_id, workload_id, name)` allocates the next integer `version` (the first is `1`) and retains every older version unchanged; scope or name isolation restarts the sequence at `1`. Concurrent creators never share or skip a version. On success it returns `201` with `policy_id`, the scope, `name`, `version`, the submitted `rule`, and a UTC RFC3339 `created_at`. Policies are persisted and survive restarts; only the rule tree (claim names and expected scalars — never evidence or claim values) is stored.
- `POST /v1/evidence/{evidence_id}/decisions` evaluates a verified piece of evidence against one policy version and records an auditable release decision. The JSON body must include non-empty `tenant_id`, `workload_id`, `nonce` (unpadded base64url), `evidence` (the same bytes received/verified — checked by SHA-256 digest, never re-verified and never persisted) and `policy_id`. Both the evidence and the policy must belong to exactly the request's tenant and workload (`404` if either is unknown or cross-scope), the evidence must already be settled `verified` (`409` for received or rejected evidence), the nonce must match the evidence's bound challenge, the evidence digest must match, and the evidence format must be one of the built-in JSON formats whose `claims` the service can read (`422` otherwise). The rule is evaluated against the top-level `claims` of the digest-matched evidence; a satisfied rule yields status `allowed`, anything else (including a missing claim) yields `denied` — both return `200` with `decision_id`, `evidence_id`, `policy_id`, `policy_version`, `status` and a UTC RFC3339 `decided_at`. Exactly one audit decision exists per evidence and policy version: retries and concurrent requests return the identical stored result. The audit row stores only identifiers, the fixed status code and timestamps — never the raw evidence, the nonce, or the evaluated claims.
- `POST /v1/release-grants` mints a one-time, TTL-bounded release grant on top of an existing decision. The JSON body must include non-empty `tenant_id`, `workload_id`, `decision_id` and `data_id`, plus an optional integer `ttl_seconds` (30–900, default 300). Only a decision whose scope is exactly the request's tenant and workload can be referenced (`404` if unknown or cross-scope), and only an `allowed` decision can authorize a grant (`409` for any other status; invalid fields return `422`). On success it returns `201` with `grant_id`, `decision_id`, `data_id`, a cryptographically random `capability` (32 bytes, unpadded base64url), `pending: true`, and UTC RFC3339 `issued_at`/`expires_at`. The capability is returned exactly once, on this response: only its SHA-256 digest is persisted, it is never logged, and it never appears on any other response. Multiple grants may be minted for the same decision/data item; each is independent. A pending grant settles exactly once: it is either consumed (via the consume endpoint or a successful payload release) or revoked (via the revoke endpoint below), whichever valid request wins the shared atomic transition first.
- `POST /v1/release-grants/{grant_id}/consume` consumes a pending, unexpired grant by presenting its capability. The JSON body must include non-empty `tenant_id`, `workload_id` and `capability` (`422` otherwise; a syntactically invalid path grant id is `422` as well). An unknown or cross-scope grant returns `404`, a wrong capability returns `401` (without settling the grant), an already-consumed or already-revoked grant returns `409`, and an expired grant returns `410` (a settled grant reports `409` even after its expiry). On success it returns `200` with exactly `grant_id`, `decision_id`, `data_id`, `consumed: true` and a UTC RFC3339 `consumed_at`. The pending → consumed transition is a single guarded update shared with the revoke and payload-release endpoints, so concurrent consumers race: exactly one succeeds and the rest receive `409` (a request that loses to a revocation observes `409 grant already revoked`), with no extra audit rows; grants are persisted and survive restarts. Along with revoke and payload release this endpoint shares the per-tenant/workload rate limit described below: after basic field validation the sixth business request in a UTC minute returns `429`. The audit row stores only the grant/decision identifiers, the scope, the data identifier, the fixed status, timestamps, and the capability digest — never the plaintext capability, evidence, claims, or any payload.
- `POST /v1/release-grants/{grant_id}/revoke` revokes a still-pending, unexpired grant by presenting its capability. The JSON body must include non-empty `tenant_id`, `workload_id` and `capability`; a missing, blank, wrong-typed or malformed field, or a syntactically invalid path grant id (including an empty path segment), returns `422` and writes no state. Judgements are made in a fixed order: an unknown grant, or one belonging to another tenant or workload, returns `404` (an unknown-but-well-formed path identifier is the same indistinguishable `404`); a wrong capability returns `401` and changes no state — the grant stays pending, so an erroneous capability can never revoke, consume or otherwise alter it; a grant already consumed or already revoked returns `409`; and an expired grant that is still pending returns `410`, with the status judgement always preceding the write. A valid request atomically settles pending → `revoked` and returns `200` with exactly `grant_id`, `decision_id`, `data_id`, `revoked: true` and a UTC RFC3339 `revoked_at`; the plaintext capability is never echoed. Repeating the revoke returns `409` and rewrites neither `revoked_at` nor any audit. Revocation shares the grant's single guarded atomic transition with the consume endpoint and `POST /v1/release/{grant_id}`: of all valid concurrent revoke/consume/release requests at most one wins, and every loser only observes the final state as `409` — when revocation wins, a subsequent or losing consume and release both return `409` and release produces no payload and no extra audit row. Revocation is scoped to the single grant; other grants (including other grants for the same data item) are untouched. This endpoint shares the per-tenant/workload rate limit described below: only requests that pass basic field and path validation consume budget, and the sixth business request in a UTC minute returns `429`. The audit record is the grant row itself, recording only the grant/decision/data identifiers, the scope, the fixed status, timestamps and the capability SHA-256 digest — never the plaintext capability, payload, data key, evidence or claims, on any response, in storage or in logs.
- `POST /v1/release/{grant_id}` releases the protected payload authorized by a one-time grant, connecting the grant to its data envelope. The path identifier must identify the same grant; the JSON body must include non-empty `tenant_id`, `workload_id`, `data_id` and `capability` (`422` for any missing, blank, wrong-typed, malformed or otherwise invalid field). Judgements are made in a fixed order: an unknown grant, an unknown or cross-scope data item, or a `data_id` different from the one the grant was minted for returns `404` (and writes no consumption audit); a wrong capability returns `401` with the grant left pending; an expired grant returns `410` (whether or not it was later consumed or revoked); and only after those checks does an already-consumed or already-revoked grant return `409`. Before any state changes, the data key is unwrapped with the master key version recorded on the envelope and the payload is authenticated-decrypted (AES Key Wrap + AES-256-GCM). An invalid keyring, a missing historical key version, damaged wrapping material, or any other decryption failure returns `500` and leaves the grant pending with no consumption audit — only authenticated-decryption success commits the one-time state. The endpoint shares the grant's atomic pending → consumed state with the consume and revoke endpoints above, so concurrent or duplicate valid release/consume/revoke requests have exactly one winner; losers receive `409` (a loser to revocation gets `409 grant already revoked` and never decrypts or releases the payload) and each successful release produces exactly one audit row (scope, data identifier, status, timestamp and capability digest) that survives restarts. On success it returns `200` with compact JSON containing exactly one non-empty string field, `payload`, terminated by a single newline; the response carries no floats, `-0.0`, non-finite values or other metadata, and the capability is used only for verification and never echoed. Like consume and revoke it shares the per-tenant/workload rate limit described below: the slot is reserved after basic field/path validation and before the 404/401/410/409/500 judgements, so a `429` reaches neither the grant nor the keyring and never releases a payload. The plaintext payload, plaintext capability and key material are never persisted, logged, or returned on any other response, and raw certificate material never enters logs.
- **Shared rate limit.** The three one-time-grant entry points — `POST /v1/release-grants/{grant_id}/consume`, `POST /v1/release-grants/{grant_id}/revoke` and `POST /v1/release/{grant_id}` — share a single budget of five business judgements per UTC natural minute per `(tenant_id, workload_id)`; all other endpoints (including grant issuance, challenges, attestation, trust roots, policies, envelopes, rewraps and the audit queries) are unlimited. A request whose fields or path identifier are missing, blank, wrong-typed or malformed returns `422` before the counter is touched: it consumes no budget and writes no state. Once basic validation passes, one slot is durably reserved in its own committed transaction *before* business judgement, so a later `404`, `401`, `409`, `410` or `500` still spends the slot; the first valid request of a minute initializes that scope's counter at one, and the sixth (serial or concurrent) request stably receives `429`. Counters are persisted by UTC minute and survive restarts; the quota is restored automatically at the next UTC minute boundary, scopes are strictly isolated and never borrow or share quota, and the reservation for an expired minute is never reused. A `429` returns compact JSON containing exactly one positive-integer field, `retry_after_seconds`, followed by a single newline (`{"retry_after_seconds":37}\n`); the value is the whole number of seconds from the current UTC instant to the next minute boundary, rounded up and at least `1`. It is recomputed for every `429` (so it may decrease within the same minute) but never extends the window, decrements the counter, writes an audit row, or otherwise affects later recovery. A rate-limit rejection changes no grant, decrypts nothing, releases no payload and writes no audit; if the counter cannot be read or written the request fails with `500` and never enters business judgement.
- `GET /v1/release-grants` is the read-only authorization-lifecycle audit: it lists release grants for one tenant/workload in stable `grant_id` ascending order with keyset pagination; the request body is always empty. `tenant_id` and `workload_id` are required non-empty query parameters. Results may be narrowed by `grant_id` or `decision_id` (canonical UUIDs), by `data_id` (any non-empty caller-chosen identifier), by `status` (exactly `pending`, `consumed` or `revoked`), and by an inclusive issuance window `issued_after`/`issued_before`, both explicit UTC RFC3339 timestamps (`Z` or `+00:00`; a naive or non-UTC offset is rejected); `issued_after` must not be later than `issued_before`. A missing/blank/whitespace/typed-wrong field, an illegal identifier or status format, an illegal timestamp, or an inverted window returns `422` and writes no state. An explicit `grant_id`, `decision_id` or `data_id` that is unknown, belongs to another tenant/workload, or (for `data_id`) is referenced by neither an envelope nor any grant in the scope returns `404`. Pagination is cursor-driven: omitting `cursor` or sending an explicit empty string starts before the smallest grant id; the compact JSON response is exactly `grants`, `next_cursor` (empty at the end) and `complete`. Cursors are opaque, HMAC-authenticated tokens carrying a kind tag and bound to the scope *and* every active filter — a forged, tampered, cross-scope or cross-filter cursor returns `422` — so replaying the same cursor always returns the identical page in the identical order, never duplicating or skipping an entry. Each entry contains the JSON-string `grant_id`, `decision_id`, `data_id`, the fixed `status`, `capability_sha256` (the SHA-256 digest only), and UTC RFC3339 or `null` `issued_at`, `expires_at`, `consumed_at` and `revoked_at`. The plaintext capability, payloads, evidence, key and certificate material never appear; the response is compact JSON with no floats, `-0.0` or non-finite values. The handler issues only reads, never writes or settles state, and returns no half page: a storage/service failure is a `500` with no partial result. Concurrent consume/revoke transitions are unaffected; a query observes only committed state, and a replayed cursor keeps its stable order across such transitions. Audit rows persist across restarts.
- `GET /v1/compliance/audit-events` is the read-only compliance audit: it lists append-only audit events for one tenant/workload in stable `(occurred_at, event_id)` ascending order with keyset pagination; the request body is always empty and no other query parameters are accepted. `tenant_id` and `workload_id` are required non-empty query parameters. Results may be narrowed by `event_id` (a canonical UUID), `event_type` (exactly `grant` or `rewrap`), `status` (exactly `pending`, `consumed`, `revoked`, `rewrapped` or `skipped`), and by an inclusive window `occurred_after`/`occurred_before`, both explicit UTC RFC3339 timestamps (`Z` or `+00:00`; a naive or non-UTC offset is rejected); `occurred_after` must not be later than `occurred_before`. A missing/blank/whitespace/typed-wrong field, an illegal identifier, type or status, an illegal timestamp, or an inverted window returns `422` and writes no state; an explicit `event_id` that is unknown or belongs to another tenant/workload returns `404`. Pagination is cursor-driven: omitting `cursor` or sending an explicit empty string starts before the smallest event, and the exclusive cursor boundary is the last returned `(occurred_at, event_id)` position. Cursors are opaque, HMAC-authenticated tokens carrying a kind tag and bound to the scope *and* every active filter — a forged, tampered, cross-scope or cross-filter cursor returns `422`, as does a cursor from the rewrap-batch or release-grant audit families — so replaying the same cursor always returns the identical page in the identical order, never duplicating or skipping an entry. The compact JSON response, terminated by a single newline, has keys in exactly the order `events`, `next_cursor` (empty at the end), `complete`. Each event contains the JSON-string or `null` `event_id`, `event_type`, `grant_id`, `decision_id`, `data_id` and `status`, plus a UTC RFC3339 `occurred_at` and `capability_sha256`; for `rewrap` events `grant_id`, `decision_id` and `capability_sha256` are `null`. No floats, `-0.0` or non-finite values ever appear, and plaintext capabilities, payloads, evidence, data keys, master keys, certificate material and plugin details are never returned or written by this path. `grant` events are inserted in the same committed transaction as the transition they record — `pending` at grant issuance, `consumed` on a winning consume or payload release, `revoked` on a winning revocation — and `rewrap` events (`rewrapped`/`skipped`) commit together with each batch per-envelope outcome or a single-envelope rotation; no event exists without its committed change and vice versa. The handler issues only reads, never writes or settles state, and returns no half page: a storage/service failure is a `500` with no partial result. Events persist across restarts, a query observes only committed state, and a replayed cursor keeps its stable order when consume/revoke/rewrap transactions commit concurrently.
- `POST /v1/data-envelopes` stores a payload under envelope encryption. The JSON body must include non-empty `tenant_id`, `workload_id`, `data_id` and `payload` (`payload` a non-empty string; invalid bodies return `422`). A fresh 32-byte data key is generated for every request: the payload is encrypted with AES-256-GCM (random 12-byte IV, 16-byte tag) and the data key is wrapped with AES Key Wrap (RFC 3394) under the current master key version (see *Master keys and rotation* below). On success it returns `201` with only `data_id`, `tenant_id`, `workload_id`, `key_version` (the version the data key was wrapped under) and a UTC RFC3339 `created_at` — the payload, data key, ciphertext and wrapped key are never returned or logged here. A repeated `data_id` within the same tenant/workload returns `409` (the same `data_id` in another scope is independent). Encryption material is written as a single atomic row (`ciphertext`, `iv`, `tag`, `wrapped_key` all NOT NULL); any encryption or write failure returns `500` with no record left behind.
- `GET /v1/data-envelopes/{data_id}` requires `tenant_id` and `workload_id` as non-empty query parameters (missing or blank → `422`). An unknown `data_id`, or one belonging to another tenant/workload, returns `404`. On success it returns `200` with the creation metadata (`data_id`, `tenant_id`, `workload_id`, `key_version`, `created_at`) plus `ciphertext`, `iv`, `tag` and `wrapped_key`, each unpadded base64url. Records are persisted and survive restarts; the read path never unwraps or decrypts, and no plaintext payload or data key is ever stored, logged, or returned. The stored material unwraps with the `key_version` master key and authenticated-decrypts to the original payload.
- `POST /v1/data-envelopes/{data_id}/rewrap` rotates an existing envelope to the current master key version. The JSON body must include non-empty `tenant_id` and `workload_id` (`422` otherwise); an unknown or cross-scope `data_id` returns `404`. The stored wrapped data key is unwrapped with the envelope's recorded `key_version` master key and re-wrapped under the current version; `ciphertext`, `iv`, `tag`, `created_at` and `data_id` are untouched, and the plaintext data key exists only on the stack for the call. On success it returns `200` with exactly `data_id`, `tenant_id`, `workload_id`, the new `key_version` and a UTC RFC3339 `rotated_at`. Re-wrapping an envelope that is already at the current version is a no-op retry that changes no material, and concurrent rewraps settle on exactly one current-version result. If the keyring is invalid, the envelope's historical key version is no longer configured, or the re-wrap itself fails, the request returns `500` and the stored row is left unchanged. Neither master keys, the plaintext data key, nor the payload ever appear in responses, the database, or logs.
- `POST /v1/rewrap-batches` rotates a page of envelopes within one tenant/workload scope without touching the single-envelope endpoint above. The JSON body must include non-empty `tenant_id` and `workload_id`, an optional integer `limit` (1–200, default 50) and an optional `cursor`. Each page selects that scope's envelopes in stable `data_id` order starting strictly after the cursor boundary; omitting the cursor (or sending an empty string) starts before the smallest `data_id`. Cursors are opaque, HMAC-authenticated tokens bound to their scope: a missing/blank/malformed value, wrong type, out-of-range `limit`, or a forged, tampered or cross-scope cursor returns `422`. Envelopes at historical key versions are unwrapped and re-wrapped under the current key one at a time (only `key_version` and `wrapped_key` change; body, IV, tag, identifier and `created_at` are untouched); envelopes already at the current version are recorded as `skipped` and change nothing. Each envelope is its own independent commit pairing the guarded material update with exactly one audit row recording the scope, envelope identifier, old/new key versions, a fixed result code (`rewrapped`/`skipped`) and a UTC timestamp — never the payload, data key, wrapped key or ciphertext. The compact, newline-free JSON response returns exactly `batch_id` (string), `processed`, `rewrapped`, `skipped`, `failed` (integers), `next_cursor` (string, empty at the end) and `complete` (boolean). A wholly invalid keyring is a server failure: the request returns `500`, creates no batch audit and modifies no envelope. If the keyring becomes unusable mid-page, a historical key is missing, or an individual rewrap fails, the page stops and the request still returns `200`: the failed envelope is left exactly as it was, gets one audit row with result `keyring`, `missing-key` or `rewrap`, `failed` is 1, and `next_cursor` stays before the failed item so a retry resumes there. Concurrent batches over the same scope advance each envelope at most once — the guarded update makes losers observe the already-current version as a skip, and replaying a `next_cursor` never re-wraps an envelope twice.
- `GET /v1/rewrap-batches/{batch_id}` returns a batch summary and its per-envelope audit. It requires non-empty `tenant_id` and `workload_id` query parameters; a missing, blank or syntactically invalid (non-UUID) batch identifier or scope parameter returns `422`, an unknown or cross-scope batch returns `404`, and a storage/service failure returns `500`. On success it returns `200` with compact JSON containing `batch_id`, the scope, `limit`, the four integer counters, `next_cursor`, the boolean `complete`, a UTC RFC3339 `created_at`, and `audits`: an ordered list of entries with `data_id`, `old_key_version`, `new_key_version` (integers), the fixed `result` code and a UTC RFC3339 `audited_at`. Batches and audits are persisted and survive restarts, so a `next_cursor` can be replayed after a restart without re-advancing processed envelopes.
- `POST /v1/rewrap-jobs` submits a persistent, asynchronously advanced rewrap job over one tenant/workload scope. The body is the same shape as a rewrap batch: required non-empty `tenant_id` and `workload_id`, an optional integer `limit` (1–200, default 50) and an optional opaque `cursor`; an explicit empty cursor (or its absence) starts before the smallest envelope. A missing/blank/wrong-typed field, an out-of-range `limit`, non-JSON body, or a forged, tampered, unverifiable or cross-scope cursor returns `422`, creates no job and changes no envelope. A wholly missing or invalid keyring, or a failure writing the job row, is a server failure: the request returns `500`, creates no job and advances no envelope. A valid request returns `202` immediately with compact JSON terminated by a single newline, containing exactly `job_id` (string), `status` (`queued`), the integer `limit`, the string `cursor` (echoed verbatim, empty for the start), and `created_at`/`updated_at` UTC RFC3339 timestamps; no floats or non-finite values appear. The durable job is then advanced by a background worker (and resumed by a startup sweep after a crash): it walks the scope in stable `data_id` order one `limit`-sized page at a time. Historical-version envelopes have only their wrapping material replaced (`key_version`/`wrapped_key`; ciphertext, IV, tag, id and `created_at` untouched), current-version envelopes are `skipped`, and each envelope is its own independent commit pairing the guarded material update with the existing `rewrap` compliance audit event — concurrent jobs over the same scope advance any one envelope at most once, losers observing it as already current. Status only migrates `queued` → `running` → `succeeded`/`failed`, each transition guarded so it happens at most once. If the keyring becomes unusable, a historical key is missing, or a single envelope fails, the job moves to `failed`: that envelope is left exactly as it was (not counted as processed), `failed` increases by one and `next_cursor` stays before the failed item; a live process does not retry it, but a process restart resumes the parked job from that cursor and it reaches `succeeded` only once the whole scope has been scanned. No payload, plaintext data key, master key, wrapped key or ciphertext is ever returned or stored on the job.
- `GET /v1/rewrap-jobs/{job_id}` returns a job's current progress. It requires non-empty `tenant_id` and `workload_id` query parameters; a missing, blank or syntactically invalid (non-UUID) job identifier or scope parameter returns `422`, an unknown or cross-scope job returns `404`, and a storage/query failure returns `500` with no half progress. On success it returns `200` with compact JSON and a single trailing newline, with fields in exactly this order: `job_id` (string), `status` (`queued`/`running`/`succeeded`/`failed`), then the integer counters `processed`, `rewrapped`, then `skipped`, `failed`, then the string `next_cursor` (empty at scope start and on success), the boolean `complete`, and finally the UTC RFC3339 timestamps `created_at` and `updated_at`. Jobs are persisted across restarts: queued jobs and running jobs whose process died (their stale claim cleared) and failed jobs parked at their failing envelope are all resumed by the new process's startup sweep, while `succeeded` jobs are never touched again.
- `GET /v1/rewrap-jobs` is the read-only asynchronous rewrap job history for one tenant/workload. The request body must be empty (any non-empty body, including whitespace, is a `422` before any state is read) and the only accepted query parameters are required non-empty `tenant_id` and `workload_id`, optional `job_id` (a canonical lowercase UUID — missing/blank/whitespace, non-canonical and uppercase spellings are `422`), optional `status` (exactly one of `queued`, `running`, `succeeded`, `failed`; anything else is `422`), an inclusive `created_after`/`created_before` window accepting only explicit-UTC RFC3339 timestamps (a naive or non-UTC offset, blank or unparseable value is `422`, and `created_after` later than `created_before` is `422`; equality is a valid single-instant window), and an optional opaque `cursor`; unknown parameters are `422`. All validation happens before any state read. An explicit `job_id` that is unknown or belongs to another tenant/workload returns `404`; a range with no matching jobs returns `200` with an empty list. Jobs are returned in stable `job_id` ascending order with an exclusive keyset cursor (internal fixed page size): an omitted cursor or an explicit empty string both start before the smallest job id, and the compact JSON body, terminated by a single newline, is exactly `jobs`, `next_cursor` (empty when the range is exhausted) and `complete`. Each entry reuses the single-job progress query's field order and types verbatim, and timestamps remain UTC RFC3339; no floats, `-0.0` or non-finite values appear. The cursor is HMAC-authenticated, carries its own kind tag and is bound to the scope and every active filter, so a forged, tampered, cross-scope, cross-filter or cursor from another query family (rewrap batch, release-grant audit, compliance audit events or revocations) is an indistinguishable `422`; replaying the same cursor returns the same page with no duplicates and no skips even while jobs' statuses are concurrently updated (the `job_id` ordering key is immutable). The handler issues only SELECTs against committed jobs: it writes no audit row, changes no job status and advances no envelope; a query failure returns `500` with no half page. History is persisted and survives restarts, and no payload, capability, key, certificate or other material is ever returned.
- `GET /v1/observability/release-summary` is the read-only release-link operational summary for one tenant/workload. The request body is always empty (any non-empty body, including whitespace, is a `422` before any state is read) and the only accepted query parameters are required non-empty `tenant_id` and `workload_id`; a missing, blank/whitespace, wrong-typed, repeated or unknown parameter returns `422`, and every such rejection happens before any state read. On success it returns `200` with compact JSON (single trailing newline) containing exactly twelve fields in this order: the JSON strings `tenant_id` and `workload_id`, then the JSON integers `pending`, `consumed`, `revoked` (the three grant status counts), `live_pending` and `expired_pending` (the pending grants split into those still within their validity window and those past expiry; the two always sum to `pending`), `rate_used` and `rate_remaining` (the current UTC natural minute's shared business-request count and the unused portion of the five-slot budget — a scope with no business request this minute reports `0` and `5`), `envelopes` (the envelope rows currently stored in the scope), `current_key_envelopes` (envelopes wrapped under the keyring's current master key version) and `historical_key_envelopes` (envelopes still wrapped under a historical version; the two always sum to `envelopes`). No floats, `-0.0` or non-finite values appear, and no capability, payload, evidence, ciphertext, wrapped/raw key or other material is ever returned — only counts and the scope. The handler takes one read-only consistent snapshot (all figures are computed by a single aggregate statement) so a concurrently committing group is never observed half-applied, and it never writes: it consumes no rate-limit budget, appends no audit row, and settles no grant. A storage failure or an unusable/missing master keyring is a `500` with no partial summary and no state change. Only committed records that survive restarts are summarized; an unknown scope is simply an all-zero range, never a `404`. Scopes are strictly isolated, and the health, authorization, envelope, rewrap, audit and X.509 entry points are unchanged.

### Master keys and rotation

Envelope encryption is keyed by a versioned set of 32-byte AES-256 master keys. Two environment variables configure them; `PROOF_RELEASE_KEYRING` takes precedence and, when set, `PROOF_RELEASE_MASTER_KEY` is never read.

- `PROOF_RELEASE_KEYRING` — a JSON object `{"current_version": <positive integer>, "keys": {"<decimal positive integer>": "<unpadded base64url of exactly 32 bytes>", ...}}`. `current_version` selects the key used to wrap new envelopes and must be present in `keys`; every entry in `keys` must decode to exactly 32 bytes. Retired versions are kept in `keys` for as long as envelopes wrapped under them still exist, so historical envelopes remain unwrappable (and rewrappable) across restarts.
- `PROOF_RELEASE_MASTER_KEY` — legacy single-key form: the unpadded base64url encoding of exactly 32 bytes, used only when `PROOF_RELEASE_KEYRING` is unset. It acts as the sole key at version `1`.

If the active configuration is missing or malformed (unparseable JSON, a non-positive or non-integer `current_version`, a `current_version` absent from `keys`, or any key that is not strict unpadded base64url of 32 bytes), envelope create and rewrap requests fail with `500` and no record is written or modified. Generate a key locally with, for example, `python -c "import base64,os;print(base64.urlsafe_b64encode(os.urandom(32)).decode().rstrip('='))"`. Keys must be kept secret and provisioned through your secrets manager outside local development.

To rotate: add the new key to `keys` under a fresh higher version, set `current_version` to it, restart, then call `POST /v1/data-envelopes/{data_id}/rewrap` for each envelope (new envelopes use the current version automatically), page through a whole scope synchronously with `POST /v1/rewrap-batches` (following each response's `next_cursor` until `complete` is true), or submit one durable background job with `POST /v1/rewrap-jobs` and poll `GET /v1/rewrap-jobs/{job_id}` — a job that stops `failed` at a missing historical key or single-envelope error leaves its cursor before the failed envelope and is retried from there automatically after a restart, settling `succeeded` only when the whole scope has been scanned. Once every envelope has been rewrapped past an old version, that version's entry may be dropped from `keys`.

Batch cursors are authenticated with HMAC-SHA256 using `PROOF_RELEASE_CURSOR_SECRET` (any non-empty secret string); a clearly labelled development-only constant is used when it is unset. Set it outside local development, and keep it stable across restarts so previously issued cursors remain replayable (a changed secret simply makes outstanding cursors unrecognizable — clients restart from the beginning of the scope, which only yields skips for already-current envelopes). The read-only release-grant audit, compliance audit-event and revocation registry cursors use the same secret and HMAC construction, each tagged with its own cursor kind and bound to its full filter set (the revocation cursor additionally binds its fixed snapshot), so no cursor family can ever be replayed against another endpoint and none of these cursors can cross scopes, filter conditions or snapshots.


### Verifier plugins

Formats are verified through a public plugin interface in `proof_release.verifiers`: implement `Verifier` (set `format_name` and `verify(context) -> VerificationResult`) and register it via `register_verifier()` on `default_registry`, or pass a custom `VerifierRegistry` to `create_app(..., verifier_registry=...)`. The verifier receives a `VerificationContext` containing the raw evidence for this call plus the tenant, workload and challenge context; the service layer never stores the raw evidence.

**Plugin security limits.** The service only ever acts on the boolean `accepted` verdict: it persists a fixed, service-defined result code (`accepted`/`rejected`) derived solely from that verdict. Any text a plugin attaches to its result (e.g. `VerificationResult.detail`) is discarded at the service boundary — it is never persisted, logged, or returned in API responses — and plugins must not embed raw evidence, key material, or other private context there. The same applies to exceptions: a raised exception maps to `500` with no state left behind, and only the exception *type* (never its message or traceback) is logged, since a faulty plugin could stuff sensitive data into either.

The built-in format `attested-nonce-json` accepts the JSON object `{"nonce": "<unpadded base64url challenge nonce>", "claims": {...}, "mac": "<hex>"}`, where `mac` is the lowercase-hex HMAC-SHA256 over the canonical JSON of `{"claims": ..., "nonce": ...}` (sorted keys, compact separators) using the per-workload key `HMAC-SHA256(secret, tenant_id + ":" + workload_id)`. The shared secret comes from `PROOF_RELEASE_ATTESTED_NONCE_SECRET` (a clearly labelled development-only constant is used when unset; set the variable outside local development). Malformed documents, nonce mismatches and bad MACs are reported as `rejected`, not as errors.

The built-in format `x509-attested-nonce-json` accepts the JSON object `{"nonce": "<unpadded base64url challenge nonce>", "claims": {...}, "certificate_chain": ["<leaf PEM>", ..., "<root PEM>"], "signature": "<unpadded base64url>"}`. `certificate_chain` is a non-empty list (at most 8) of PEM certificates ordered leaf-to-root, and `signature` is produced by the leaf private key over the canonical JSON of `{"claims": ..., "nonce": ...}` (sorted keys, compact separators) — RSA PKCS#1 v1.5 with SHA-256, ECDSA with SHA-256, or Ed25519, depending on the leaf key type. After the service's identity, nonce and digest checks, the verifier requires: a parseable chain whose root is byte-identical to a trust root configured via `POST /v1/trust-roots` for exactly this tenant and workload, every certificate within its validity period, every issuer a CA certificate, each certificate signed by the next in the chain, and a valid leaf signature. Any format, chain, trust, validity or signature failure settles the evidence atomically as `rejected` (still `200`); certificate material, evidence content and exception details are never persisted, logged, or returned. Verifiers receive the configured trust roots for the request's tenant and workload through `VerificationContext.trust_roots`.

Before the verifier runs, the service computes the same unpadded-base64url SHA-256 DER fingerprint for the root, every intermediate and the leaf certificate of an `x509-attested-nonce-json` chain, identifies the configured trust root the chain anchors to (locking its row), and applies two short-circuits that settle the evidence as rejected without invoking the verifier or computing any certificate signature. First, when the anchor trust root has been retired via `POST /v1/trust-roots/{root_id}/retire`, the evidence is rejected immediately — this precedes the revocation check, the workload identity gate and the signature verifier. Second (only for an active anchor), when any chain certificate matches a revocation registered via `POST /v1/revocations` under that trust root whose `effective_at` has arrived, the evidence is likewise rejected. Neither short-circuit changes the `attested-nonce-json` HMAC format, custom verifier plugins or any other endpoint. Both take place inside the evidence's settlement transaction and are ordered against retirement and registration on the same trust-root row, so only a retirement or registration committed before the evidence atomically settles can affect it; one that commits later is never applied retroactively and repeated verifies keep returning the stored conclusion. If the anchor status or the revocation registry cannot be queried, verification returns `500` and the evidence stays `received`, so it can be re-verified once the registry recovers.

After the chain, signature, validity and revocation checks have passed, X.509 verification consults the *active* workload identity profiles registered via `POST /v1/workload-identities` under the exact trust root the chain anchors to (profiles revoked via `DELETE` are skipped entirely but remain queryable). When no active profile exists for that anchor, the ordinary verification result is returned unchanged (fully backward compatible; this includes an anchor whose profiles were all revoked). When one or more active profiles exist, the leaf certificate's parsed issuer DN, parsed subject DN and subjectAlternativeName URIs are compared as strings against every claim; verification may continue only if at least one claim of at least one profile has its `issuer`, `subject` and `uri` all exactly equal (RFC4514 issuer/subject and one of the leaf's SAN URIs) — if the anchor has active profiles but none hit, the evidence settles atomically as `rejected` (`200`), exactly like any other rejection. This gate changes only the X.509 format's verdict: the HMAC format, custom verifier plugins, challenges, evidence receipt, policies, authorization, envelope and rotation endpoints behave exactly as before. Profiles (including claim-set replacements via `PUT` and revocations via `DELETE`) are read inside the evidence's settlement transaction against the same trust-root lock the lifecycle writes take, so verification observes only committed, active profiles: an update or revocation that has not committed before settlement neither affects that verification nor is applied retroactively, a replacement committed before settlement is seen by that verification, and a settled conclusion is never rewritten by a later update or revocation. If the profile registry cannot be queried, verification returns `500` before any state is written; the evidence stays `received` and the identical call can be retried after recovery, with no half-finished conclusion. Profiles are strictly scoped — a profile under one tenant, workload or trust root never gates evidence in another — and only the non-sensitive comparison strings are stored; certificate material and evidence content never enter the database, logs or responses.
